# 候选界面审阅与确认

用户要求手工逐份审阅时，按授权确定候选工作区、审阅渠道和推进顺序。待审候选需与正式安装隔离。若调用者依赖仍待批准的 Skill，等依赖具备后再发布。

## 审阅者应看到什么

- 准确 ID、Description、完整的渲染和原始 `SKILL.md`、实际文件清单和内容。新增说明写清每份 Reference 的用途。更新既有 Skill 时展示文本差异。
- 哪些 Skill 相邻、触发条件如何区分、谁调用目标 Skill、传入什么以及期待什么结果。
- 项目 Reference、宿主和插件依赖、已验证的行为及限制。涉及路径时展示实际解析根、换位置后的验证和受阻项。缺失驱动、隔离演练和真实平台运行按其实际范围标注。

## Git 与 IDE 审阅

用户要求 Git/IDE 审阅时，使用获授权工作区的最终源码路径，保留未跟踪及未暂存状态。以 Git 忽略目录镜像候选真实文件树。Markdown 保留原路径和文件名，其他文件仅追加 `.md`。每页先给实际文件链接和变化概要，再按候选原顺序完整展示正文及原行号。

以自然段、同主题的整组规则或列表、完整逻辑代码块为说明单位。标上游与候选的实际位置。解释前先判断该组有哪些阅读、检索、调用或行为关系会在转写中丢失，再选值得讲的事实。

- 以实际问题组织分析，说明发现了什么关系、凭什么确认、为什么采用该写法，以及另一种读法会导致什么实际动作。可以用保留、改写、移除帮助表达一项取舍。相同字段可短定位；稳定组没有实质取舍时无需逐项点评。
- 原标记可能用于查资源时，按[标记核对](entry-writing.md#核对-markdown-标记背后的引用)检查原词到实际目标的路径。用读者或调用者的动作反验，例如能否区分同名入口、能否从英文标题推回正确 ID、会不会尝试加载未迁能力。
- 改用表格等结构时，在有取舍的组解释原版结构表达了什么、新版为什么更好查，以及哪个约束需要保留原形。

让用户可用文件路径和段落或行号反馈。正文维持自然分组，避免逐行或逐条重复注释。

默认交一个目录索引。固定原文快照、内部中译、绑定摘要、日志及差异映射留内部。用户选择的原文解读稿随索引交付。验证目录一一对应、全文回读、注释分组与实际链接，再绑定本次候选和审阅材料。网页快照用于用户选择或确需该渠道的情况。

## 双文件审阅

用户选择先理解上游再审候选时，同一目标相对路径交两份 Markdown，彼此互链。索引先列原文解读，再列候选与迁移说明。

- **原文解读**先说明文件在上游的职责、读取者和读取时机。用 `1`、`1.1`、`1.2` 显示章节层级，每节以「本节职责」开头。随后按原顺序分组完整呈现固定版本的英文与原行号，再集中解释组内各句或各条。保留条款之间的并列、先后和例外关系。
- **候选与迁移说明**按实际文件顺序分组。每组使用一个代码块，上半完整放对应固定英文及原行号，下半完整放该组中文候选及实际行号。保持各自源码格式，包括加粗标记、代码、链接和两列表格。语义移动时定位其原组，纯新增或移除照实写清缺少哪一侧。两份文档仍互链。
- 解释写在对照块之后，聚焦只有查证或比较才能发现的关系、结构取舍和执行后果。Description 仍按[写法与验收](frontmatter-policy.md#description-的写法与验收)先核定完整原文承诺；同组英文放全文。可同时让审阅者看到英文标记和它在中文里的对应位置，无需在说明里重复抄写。
- 全文核对源码和行号、原词到目标的追踪、确实能区分结论的情形和实际渲染。栏目数量、文字长度和是否用了固定格式不作为语义通过的依据。

### 候选写法与取舍

- 先找出这一组要帮助读者做的一个判断。候选优先写影响该判断的条件、动作和后果，把只在其他步骤消费的细节留到其首次使用处。审阅说明解释这个写法为什么合适，并指出删减、移位或保留对实际用法的影响。
- 对照块后的说明分条写。每条先用加粗的完整句子直接说出候选作出的具体选择，再用相关场景、真实调用或会改变结果的另一写法支撑。一个组可以有不止一条，但都围绕同一个问题。一般只展开会影响读者决策的取舍。
- 原文的定义、特点和转述由原文解读与对照块承载。说明中引用原文只为支持一个实际选择。用可判别的场景解释为什么这样写，省掉字段盘点、候选正文复述和任何文件都能套用的原则宣讲。
- 复审时先只看各条加粗句，检查能否看出候选实际选了什么。再读支撑，检查场景和证据是否解释其必要性或影响。结论与支撑分开可读。若删去一句后仍能用同样理由作出同样判断，这句可精简。

### Token 对比

需要比较迁移篇幅时，按审阅稿的现有语义组，显示英文、中文的 token 数、差值和相对英文的增减百分比。全文同时独立编码并显示总计。分组分别编码，跨组可能合并 token，因此分组相加未必等于全文。英文为零的组显示新增和实际增量，百分比留空。

使用[通用 Token 计数](workflow.md#文本-token-对比)的分词器和差值口径。按实际源码计入 frontmatter、Markdown、空白和换行。审阅标题、行号、围栏、批注与统计本身排除在计数之外。中文候选中的英文名称、路径及迁移内容仍按其源码计入。按[查重与保真复核](workflow.md#查重与保真复核)说明主要增减对应的行为、必需引用和可收拢的重复。

从治理 Skill 源码目录运行。分组 JSON 的 `groups` 每项包含 `title`、`english`、`chinese`，两种语言各用 1-based 的首尾行，缺失一侧写 `null`。首次运行需要分词器依赖和词表缓存。

```sh
uv run --script scripts/count_review_tokens.py "$upstream_source" "$candidate_source" "$review_plan"
```

### 解读要让首次阅读者能作决定

- 专名首次出现时说明它是什么实体、在哪里、谁会使用。将指代还原成具体角色、文件或动作，并交代适用范围。
- 对会改变行为的规则写清触发条件、判断者、命中后的动作、执行顺序、结果及停点。保留原文的强制程度、数值边界与例外。分清作出调用或委派决定的条件，以及决定后、动作前要满足的条件。
- 沿实际调用确认动作是直接执行、读取包内文件、打开内部流程、加载其他 Skill，还是调用外部能力。按实际需要查清入口、输入、输出及依赖缺失时的影响。说明理由并给出出处，写明哪些属于原文事实、根据调用关系作出的推断、迁移适配或宿主实测。宿主自动注入、缓存和单次模型调用行为以实际证据为准。
- 简单条目用短句。容易误读且会改变行为的条款，用具体情形检查读者会怎么选、怎么执行。阈值、例外或相似规则影响结果时，加能区分结论的边界例子。

### 派发与复审

- 按用户约定先审各类代表样例或逐份推进。采用样例时，从本 Skill 已有文件种类中各选一个代表，按用户约定确认后展开其余文件。采用逐份审阅时，按约定收口当前文件再进入下一份。
- 派发单文件任务时，交代读者、固定上游与实际候选、适用审阅规则、本文件重点核对的调用和行为，以及能验证理解的例子。负责该 Skill 的会话直接接收按相对路径与段落给出的反馈，组织修订与复审。分设总控时，整份交付、实际审批结果和确需跨 Skill 决定的事项统一回传总控。
- 收到当前文件的反馈后，先从固定原文和实际调用独立写出能复现问题的情形及预期。定位缺口属于输入、语义还原、转写、审阅规约或呈现。先修正缺口所属的输入或过程，再按[语义还原](entry-writing.md#先还原原文要求的行为)审查本文件同类问题。
- 冻结本文件上次运行的上游版本、反馈前候选、任务目标、实际调用材料和宿主约束。用同一份任务上下文和更新后的规约，在隔离位置以原审阅流程重新处理整份文件，重新生成候选和对应审阅稿。先按反馈前候选的段落顺序列出整文件转写计划。每组标出原文和调用证据、执行者据此要完成的动作、保留或订正及可检查的理由。按计划生成全文及审阅稿，沿用已有且成立的章节、入口位置和顺序。只有用户要求重排或已有证据证明就地订正无法解决问题时，才在计划中登记受影响入口、迁移方式和验收，再调整结构。保留已确认的原文解读供用户回查。给生成者实际发生的情形和需复核的行为边界，不给具体写法。独立验收预期、上次人手修稿和参考答案留给核验者。生成者先用已知情形自查转写计划和成稿。
- 先对照转写计划与实际差异，核查未登记的重排、删减及行为变化。用隔离候选执行项目原有的入口和交付检查，验证已有消费者按原契约读取。如失败，把真实失败和对应调用处交回生成步骤，用同一上下文修订并重新生成全文与审阅稿。再核对本次实际产物能否通过反馈案例、全文同类检查、原文与候选行号保真、标题与链接渲染。未通过时继续定位并修订规约，使用同一基线再跑。通过后才把经核验的结果订正到主候选，核对工作区实物，并交用户确认当前文件。当前文件获确认后才启动下一份。
- 分别记录样例或文件级确认、整份候选批准及正式发布授权的出处和范围。候选批准绑定实际版本和审阅快照，发布按实际授权执行。

## 网页快照与批准检查

涉及直接共享文件时，将这些文件的文本差异填入 `shared_diff`，并在 `shared_files` 登记仓库相对路径到实际文件 SHA-256 的映射。生成和确认时都加 `--workspace "$source_root"`，共同核对共享变更。把上述面向审阅者的说明填进 [审阅资料模板](../templates/review-context.template.json)。使用 `uv` 运行生成器。首次准备 Markdown 渲染依赖时需要依赖缓存或网络。网页产物可离线打开。

```sh
uv run scripts/review_skill.py "$candidate" --baseline "$baseline" --context "$context" --out "$review_dir"
```

新建 Skill 省略 `--baseline`。用户可用候选页核对内容。只能用手机审阅时，在 Codex 聊天中先展示本次实际改动、验证及版本，再按需贴同一快照的原文与差异。用户可在当前对话中按文件反馈或确认这份候选。人工确认记录的字段为 `skill`、`status`（`approved`）、`fingerprint` 和 `evidence`（实际确认出处）。确认前不存在通过记录，工具不会代替审阅者填写。

```sh
python3 scripts/review_skill.py "$candidate" --context "$context" --check-approval "$approval_file"
```

检查把确认绑定到实际候选文件和审阅资料的摘要。文件增删、运行资源变化或审阅资料更新都需要核对新版本。校验器只核对记录存在及摘要匹配，人工确认的真实性仍须从对应出处核实。审批快照和报告留在本轮工作目录，避免一起安装。使用获授权的正式源码路径审阅时，核对实际安装的链接是否会提前读取候选。
