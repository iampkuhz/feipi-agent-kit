# 行为评估方法

本文件只供维护时使用，不进入运行上下文。用例与必须保留的行为见 cases.json，实际输出和记录写到仓库 tmp/skill-evals/feipi-writing-refine-text/。

## 执行

给独立执行者 skill 入口和原始用户请求，不提供 expected、forbidden、旧输出或修改结论。要求完成真实任务，并在正文之外记录实际读取的规则文件。输入材料彼此独立；不要用前一个案例补全后一个案例的背景。

用例含 `input_file` 时，把该文件全文作为材料附在 `prompt` 后；只传执行所需的 skill 入口、请求和原文，不让执行者扫描 evals。长文用例另有 `reference_file`、`expectations_file`、`provenance_file`，这些只供评估者使用。来源、状态与协作验收方向见 [数据说明](README.md)。

检查维度：

| 维度 | 通过证据 | 失败表现 |
|------|----------|----------|
| 条件加载 | 真实读取记录与本次目标交付物一致；只在材料有触发条件时读取历史方法 | 汇报任务读取邮件或纪要细则，或者遗漏必要公共标准与历史方法 |
| 语义去重 | 同一用途的重复命题合并，部分重合的差异保留 | 按同词误删不同范围，或保留连续的同义重复 |
| 有效逻辑 | 因果、条件、对比、顺序或例外仍能准确理解 | 为去过渡词删除约束，或把不同关系互换 |
| 历史与问答 | 正确处理更正、建议、未决分歧、代号与问答 | 最新发言自动当事实；问题变成答案；起草过程泄漏进正式正文 |
| 解释完整 | 读者能理解核心结论及必要依据、条件与行动；缺口单列 | 只剩短标签，或者通过编造机制和数据补解释 |
| 文体与范围 | 保持目标文体、作者声音、格式和授权范围 | 所有文本变成报告或口语；审阅任务直接写回 |
| 信息保真 | 逐项对照对象、数据、来源、状态与判断强度 | 关键事实丢失，建议变决定，计划变承诺，未知变确定 |
| 问题识别 | 问题有真实原文锚点和具体依据，明确问题与疑点分开 | 陌生术语自动判错、已说明的业务未决当成表达错误、改写后倒推原文有错 |
| 修复与交接 | 默认给正文和原文问题清单；已修复项保留，状态与实际修改相符，缺知识时给具体交接信息 | 只给改稿、只列剩余问题、未落实却标已修复、凭空补专业含义、在正文塞诊断批注 |

只有当前用例涉及的维度需要判断。每项写出输出中的证据或具体缺失，不能以总体“读起来更好”代替。任一关键事实、限制、冲突或证据被篡改则本例失败，不能靠其他维度高分抵消。

真实文档用例按 `expectations.json` 中每个稳定 ID 逐项记录 `pass` / `fail` / `not_run` 及输出证据。`must_include` 可以合并表达；`must_exclude` 判断错误内容和用途，不是匹配禁词。原文、输出与拟定参考稿需要交叉核对，不能因输出不同于参考稿就判失败，也不能因接近参考稿就判通过。参考稿仍处于 `proposed` 时，评审通过只代表符合当前拟定标准，不能写成用户验收通过。

每项 `scope` 默认为 `body`，只检查优化正文；`scope: issue_list` 检查问题清单。定位所需的原文引用允许出现在清单中，不应误判成正文仍有黑话。分别报告识别质量与修复质量：识别准确但缺资料无法修复，可以交接；改写流畅但漏报或误报问题，不能算诊断通过。用户明确只要正文或只审阅时遵循该请求，仍核查相应边界。

## 比较与结论

- 使用同一原始请求比较改造前后版本时，分别独立执行；旧版本通过也如实记录，不预设改造必然获胜。
- 自动脚本只能证明结构、链接和用例完整性。词数、关键词命中或压缩率不证明语义质量。
- 自检、独立执行、人工逐项评审、真实用户材料验收分别报告，不能混用。未跑的用例标为未验证。
- 修复后重跑受影响的行为；加载架构变化要复核相关场景。不要用已生成的手写示例冒充模型执行结果。
