# 消息与自然回复

适用于邮件、工作消息、聊天和评论答复。可以精炼已有回复，也可从对方原话和用户要点拟稿。自然感来自对这次交流作出合适回应；不以加语气词、错别字或表情符号模拟真人。

## 先判断这轮需要回应什么

从材料确定接收者、关系距离、对方这句话的作用，以及用户希望表达什么。对方可能在求答复、确认安排、提出异议、请求帮助、分享感受或单纯寒暄；不要把每种话都转为知识讲解或行动计划。

区分对方已知的背景、用户给编辑者的备注、这次需要告知对方的新信息。当前回复可以承接双方已知的对象，不必重写整个背景；换了接收者、话题或原文指代仍不明时才补必要说明。给编辑者的情绪备注、写作要求和风格示例不直接发给对方。

材料已给出用户的立场就直接表达，保留不同意、拒绝、犹豫或限制，不为了友好改成赞同。若同一句对方来话可能得到相反答案，而材料没有用户态度或事实，询问决定答复的最小缺口；不要猜愿意参加、能按时完成或承诺稍后处理。

## 提炼重点

- 先回答当前问题、给出已有决定，或作出合适的情绪回应。再保留会改变对方理解、判断或下一步的理由、条件、请求与链接；末尾不重复总结。
- 对方已知道的背景、内部排查过程和推演细节通常不必复述；对方明确追问原因、证据或步骤时，给够所需说明。多个独立问题逐项处理，未知项如实说明，不用“简短”掩盖漏答。
- 篇幅随任务变化。一句能说清就一句，需要解释再展开；不固定“三点”“一句结论加一个行动”，也不统一删除列表。已请求的结构、必要步骤与关键限制保留。
- 对工作安排，保留动作主体、时间、时区、附件与收件人范围；“请确认”“建议”“预计”不能改成命令、决定或保证。用户的意向不升级为代表他人的决定。

## 常见的不自然表现与处理

这些是上下文中的编辑线索，不能单凭措辞判断作者身份。

| 表现 | 交流中哪里出了问题 | 处理 |
| --- | --- | --- |
| 先说“你的核心诉求是”，再复述对方整段话 | 把回应写成对接收者的分析，答复迟迟不出现 | 直接接关键问题；确需澄清时只复述有歧义的部分，不替对方定义深层动机 |
| 每次都有小标题、三条建议和结尾总结 | 用相同模板处理不同大小的问题 | 按实际信息组织；简单聊天用短段，复杂事项保留有用的分点 |
| “当然可以、你说得非常对、希望对你有帮助”反复出现 | 泛化的服务口吻取代具体回应 | 删除无作用的夸赞和包装；真实的感谢、确认、祝贺和礼貌保留 |
| 两边都分析，却不表达用户已有的选择 | 把面面俱到当成帮助，隐藏了真实立场 | 明确材料中的态度，给必要理由；材料没有选择则不捏造 |
| 一句吐槽得到长篇共情和解决方案 | 情绪强度过大，也擅自改变了对话目的 | 接住具体处境，回应力度与关系匹配；没有求建议时不自动布置任务 |
| 为了亲切，加入“我也经历过”、保证或过度熟络的称呼 | 用虚构经历与承诺制造关系感 | 只使用用户提供的事实和真实意图；不凭空增加经历、心情、忙碌理由或可用时间 |
| 硬塞“哈哈、懂的、兄弟”、省略号或故意写错 | 只改表面口语标记，可能偏离用户习惯 | 有样稿时参考句长、用词和标点；不复制样稿旧事实，也不夸大其风格 |

保留关系所需的温度。对老师或客户保留适度称呼、请求和感谢；对朋友保留真实的轻松、关心或庆祝。礼貌、情绪、第一人称和专业术语都不是禁用项，不把自然回复统一改得冷淡、随便或刻薄。

## 交付与 AI 验收

- 待发送回复独立成段，诊断或依据放在其外；不夹入“我采用了什么策略”等编辑说明。用户明确“只给回复”“只回一句”“不要分析”时，只交付可发送文本。没有要求时给一个合适版本，不批量堆选项。
- 有待改草稿，问题清单定位该草稿，区分已修复与材料缺口；只有对方原话和用户要点时，不制造“原文表达错误”，仅按入口要求说明依据或缺口。
- AI 将成稿接在对方原话后检查：是否真正接话，是否漏答，是否重复了对方已知内容，语气是否符合关系；再核对事实、立场、否定、条件和承诺均有依据。不要用“像人”作为删除信息或捏造态度的理由。
- 不要求用户复述或给自然度打分，也不让用户代做保真检查。只拟稿，不自行发送消息。
