## 2026-08-09｜第一轮：内容与图示质量

### 1. 组件总览的顶层拆分失真

- [x] **状态：已完成**

## 2026-08-09｜第三轮：历史可读性与创新价值

### 13. 历史记录过于简略，表格难以阅读

- [x] **状态：已完成**
- 你指出的问题：原记录每项只有一句“问题”和一句“优化摘要”，缺少背景，无法理解为什么要这样改；表格也不适合承载多层解释。

### 14. 创新点没有和价值关联

- [x] **状态：已完成**
- 你指出的问题：当前创新点主要说明某个环节“怎么处理”，但没有说明现有做法是什么、与现有做法相比改变了什么，以及这种改变有什么好处。
- 主要影响：创新点会退化成实现步骤。评审人只能看到“我们怎么做”，看不到“为什么这构成差异”和“差异为什么产生价值”。
- 已做优化：每个创新点必须连续写出以下链路：
  1. 对比基线：来源事实支持的现有做法，或不指向具名竞品的通用技术做法。
  2. 本方案处理方式：具体采用什么核心机制。
  3. 实质差异：技术对象、关系、状态或约束相对基线发生了什么变化。
  4. 价值关联：为什么上述差异会产生对应价值，不能只写“更高效”“更安全”。
  5. 可观察效果：通过 `effect_id` 绑定唯一 `T`，说明最终能观察或验证什么结果。
- 落地方式：manifest 新增 `comparison_baseline`、`value_link` 和 `effect_id`；模板把五项放在同一个创新点下连续展示；校验器拦截字段缺失、泛化价值和双向 `I/T` 映射不一致。
- 证据边界：没有外部证据时只能与来源事实中的现有做法或通用技术基线比较，不能为了说明“别人怎么做”而虚构具名竞品能力。

## 2026-08-09｜第四轮：实现基础与保护边界

- [x] **状态：已完成**

- 已做优化：每个创新点都必须先填写“已实现基础”，包含技术对象、触发或输入、实际处理、必要边界、输出或状态以及来源事实编号；这些内容保留真实技术路径，但必须泛化类名、函数、字段、表结构和内部产品名。

- 阶段与图示：写作思路阶段明确展示 `IE` 供内部确认；最终图示只画已实现路径，拟扩展统一留在正文高亮块和内部附录，避免图中重新混淆实现与扩展。
- 验证方式：新增 `INV-007`，拦截缺少实现基础、实现来源悬空、照搬内部标识、`IE` 台账与创新点不一致、存在孤立 `IE`、扩展字段不完整以及扩展正文未真正进入高亮块等情况。
- 验证边界：脚本只能检查分类和来源记录是否完整，不能证明某项功能在真实产品中已经实现；最终分类仍需你在写作思路确认阶段确认。

## 2026-08-09｜第六轮：竞品研究完整性

### 18. 缺少竞品输入时直接留空或写“待检索”

- [x] **状态：已完成**
- 你指出的问题：行业竞品分析不能因为用户没有提供竞品材料就什么都不写，也不能只输出“待检索”之类的占位说明；skill 应主动搜索一些相关行业方案。
- 主要影响：竞品章节虽然避免了虚构事实，但没有提供任何行业参照，无法帮助判断本方案与现有产品、公开方案的关系，也会把本应由撰写流程完成的研究工作重新推回给用户。
- 已做优化：无论用户是否提供竞品，都至少执行两组公开资料检索，分别覆盖泛化后的技术对象和核心机制；manifest v1.2 要求记录检索依据词、跨分类或使用场景上下文词、检索式、日期、实际查阅页面和结果摘要，并校验这些技术词与已确认输入、关键词和实际检索式同源。
- 输出方式：找到可靠资料时列出 1–3 项有来源的竞品或相似方案；确实没有可用证据时，也必须展示检索范围、日期和具体结论，不能留空或出现“待检索”。
- 失败处理：检索工具不可用或检索记录不完整时暂停最终成稿，不用占位文本伪装成已完成；本地脚本只验证检索记录是否完整和自洽，不能证明网络搜索真实发生或外部事实绝对正确。
- 验证方式：新增 `INP-004`、`CMP-005` 等稳定规则，覆盖伪造/私网地址、缺少技术上下文的无关检索、HTML entity、零宽字符、输入自污染、重复检索、空摘要、无证据时具名断言和中英文占位符；完整回归 101/101 通过，并用一个未提供竞品名称的独立请求验证能够先主动检索、再停在写作思路确认阶段。
- 能力边界：脚本只能确认检索记录具有已绑定的技术依据、上下文和研究意图，不能判断检索式其余自由文本是否语义相关，也不能证明网络检索真实发生；这两项必须由执行阶段检查实际查询和页面。

## 2026-08-09｜第七轮：输出目录隔离

### 19. 外发稿与内部过程产物混在同一目录

- [x] **状态：已完成**
- 你指出的问题：最终外发版、内部追溯稿、manifest、验证报告和图包平铺在同一个目录，Git 无法只追踪最终产出；希望所有中间产物进入一个可统一加入 `.gitignore` 的固定子目录。
- 主要影响：提交时容易误带内部来源、检索记录和校验工件，也难以通过一条递归忽略规则保持仓库只追踪外发稿。
- 目录名决策：使用 `disclosure-workspace`，不使用 `disclosure-package`。因为最终外发稿位于目录外，`package` 容易被误解为完整交付包；`workspace` 更准确表示内部稿、事实模型、图包和临时过程文件组成的工作区。
- 已做优化：交底书目录根部只保留唯一 `disclosure.md`；内部稿、manifest、validation、图包及所有落盘的检索记录、写作思路和临时草稿统一进入同级 `disclosure-workspace/`。根 `.gitignore` 可使用 `**/disclosure-workspace/`。
- 兼容策略：主校验入口参数仍是交底书目录；旧平铺目录只做带警告的读取兼容，新旧 manifest 同时存在、内部工件泄漏到根部或工作区复制外发稿时直接阻塞。
- 验证方式：新增 `PKG-012`、`PKG-013` 与布局回归，覆盖新布局、旧布局警告、双布局歧义、根部内部文件泄漏、工作区重复外发稿、验证报告落点及工作区符号链接越界；完整回归 107/107 通过。
