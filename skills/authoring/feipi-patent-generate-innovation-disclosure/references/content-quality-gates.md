本文件是交底内容规则真源。脚本负责可确定判断；人工复核负责业务边界、因果语义和 SVG 可读性。不要把“存在复核记录”表述为脚本已理解内容。

## 1. 验证状态与编号

### 最终状态

- `success`：所有确定性规则通过，所有必做复核为 `pass`。允许存在“已检索但无可用证据”等诚实结论。
- `review_required`：确定性规则通过，但至少一项必做复核为 `pending`。
- `blocked`：确定性规则失败，或至少一项必做复核为 `fail`。

### 进程退出码

- `0`：`success`
- `1`：`blocked`
- `2`：`review_required`

### 可见编号

- `D1...Dn`：图示。
- `E1...En`：组件、模块和部署结构关系。
- `S1...Sn`、`S5.1...`：主流程及子调用。
- `I1...In`：创新点。
- `T1...Tn`：技术效果。

专利文档禁止使用 `M/R`。通用时序图只有在非专利的 `interaction_mr` 模式下继续使用 `M/R`。

`SF/IE/EM/C/BD/SYS/PB` 是内部台账编号，只能出现在 manifest、内部追溯附录和阶段 2 确认材料中，不属于对外可见编号。

## 2. 输入与边界

### INP：成稿门槛

- `INP-001`：专利名、使用场景不能为空。
- `INP-002`：技术对象、核心机制、必要约束、现有问题事实各至少 1 项。
- `INP-003`：至少具备一条可追溯到来源事实的已实现技术路径，并在写作思路中确认哪些机制已经实现、哪些只是拟扩展保护；无法确认时必须追问并暂停成稿。
- `INP-004`：输入完整性中的技术对象和核心机制必须在同类关键词中保留精确落点，不能为了让无关检索通过而单独改写输入字段。

正例：输入明确“运输异常处置单”“阶段化窗口”“不改变采集频率”“单点阈值造成重复派单”。

反例：只有“建设智能平台，提升效率”，直接补齐模块和效果并成稿。

### BND：顶层边界

- `BND-001`：`boundaries` 必须包含业务域、系统归属、物理边界和部署触发四类结构。
- `BND-002`：业务域写明范围，独立系统写明拥有方与边界，物理边界写明类型与说明。
- `BND-003`：组件总览顶层只允许业务域、独立系统和物理端点；类、函数、JAR、处理器类、数据库字段和表名出现在顶层时阻塞。
- `BND-004`：部署触发只允许约定枚举，禁止自由文本造成条件漂移。
- `BND-005`：存在部署触发条件时必须至少声明一个物理边界。
- `BND-006`：正文与台账一旦出现跨网、跨链、在线/离线、HSM、人工摆渡或人工交接语义，必须声明对应触发标志，不能靠漏填标志绕过部署图。

正例：顶层为“运输监测域”“异常处置系统”“现场执行端”。

反例：顶层为 `TemperatureProcessor`、共享 JAR 和 `alarm_record.status`。

自动门禁可识别显式实现项和必填边界字段；“某对象是否真是独立系统”必须人工复核。

## 3. 图示职责与密度

### FIG：图示集合

- `FIG-001`：每个 PlantUML 块前必须有唯一 `diagram-id` 标识。
- `FIG-002`：manifest 图示清单必须为对象数组，使用连续 `D` 编号和已注册职责。
- `FIG-003`：`component_overview` 与 `main_flow` 各恰好一张；触发部署条件时 `deployment_boundary` 恰好一张。
- `FIG-004`：结构关系使用从 `E1` 开始的连续编号。
- `FIG-005`：结构边标签只允许为空或 `E1...En`；完整说明放在图下。
- `FIG-006`：图包必须 `final_status=success`、`render_result=ok`，`brief/coverage/layout` 三项检查均为 `ok`，且职责与 typed profile 匹配。
- `FIG-007`：文档、manifest 和内嵌 PlantUML 的图示集合必须一致。
- `FIG-008`：结构图不超过 8 个节点、10 条可见边、单节点 4 条连接；指标来自图包 `metrics`。
- `FIG-009`：每张图必须声明不同的唯一目的；与总览或主流程重复时删图。
- `FIG-010`：PlantUML 与 SVG 只呈现已实现技术路径，不得写入内部编号、泛化前术语或拟扩展保护内容；每张图的视觉复核记录必须明确确认“仅呈现已实现路径”。

`module_detail` 还必须指定一个 `parent_component_id`，且只细化该组件；该约束由 component typed profile 校验。

正例：D1 只说明三个独立系统的边界，E1–E3 的语义在图下解释。

反例：D1 同时画类、数据库字段、完整业务流程和异常分支，共 14 个节点。

节点、边、连接度、内部编号、原始术语和与台账完全相同的扩展文本可自动判断。线条交叉、文字遮挡以及图中是否只呈现已实现语义必须在最终 SVG 上人工复核，并把结果绑定到 `svg_sha256`。

## 4. 流程编号与标签

### FLOW：主流程

- `FLOW-001`：主流程顶层步骤数量为 5–10。
- `FLOW-002`：顶层步骤使用从 `S1` 开始的连续编号。
- `FLOW-003`：子调用使用 `Sx.y`，且父步骤必须存在。
- `FLOW-004`：专利文档和图示不得混入 `M/R`。
- `FLOW-005`：箭头或活动标签只保留一个不超过 20 字的动作短语；参数、异常和长解释放在图下。
- `FLOW-006`：主流程图与图下正文的 `S` 步骤集合必须一致。
- `FLOW-007`：专利主流程禁用 `autonumber`；时序主流程的 brief 必须声明 `numbering_scheme: process_s`。

正例：图中显示“S5 派发任务”，正文在 S5 下解释责任参数；S5.1/S5.2 表达同步子调用。

反例：箭头写“S5 系统根据合同、位置、温度和时限计算责任团队并在失败时转人工”。

编号、连续性、父子关系和标签长度可自动检查；动作是否准确表达业务语义由人工复核。

## 5. 关键词

### KWD：分类合同

- `KWD-001`：总数固定为 5–8 个，并满足技术对象 1–2、核心机制 2–4、关键约束 1–2。
- `KWD-002`：每项必须同时提供非空 `term` 和正文 `anchor`。
- `KWD-003`：三组互斥，禁止重复或同义词堆叠。
- `KWD-004`：禁止孤立使用“平台、模块、系统、安全、高效、智能、优化”等泛词。
- `KWD-005`：禁止内部变量、未授权产品名和未进入白名单的缩写。

正例：技术对象“异常处置单”；核心机制“阶段化异常窗口、责任域映射”；约束“采集频率保持”。

反例：“系统、平台、智能、安全、高效、优化”共六项。

数量、重复和禁用词可自动判断；关键词是否真正具有区分度需要人工复核。

## 6. 核心主张与创新点

### INV：创新结构

- `INV-001`：全篇只有一句核心发明主张，写全技术对象、核心机制、必要约束和实质差异。
- `INV-002`：保留 2–4 个 `I1...In`，编号连续。
- `INV-003`：每项必须包含对比基线、核心机制、必要约束、实质差异、价值关联和对应 `T` 编号。
- `INV-004`：每项必须至少提供一个有效 `D/E/S` 落点。
- `INV-005`：普通分层、组件拆分、接口封装或文字改名不得单独算创新。
- `INV-006`：每项必须形成“现有做法 → 本方案处理方式 → 实质差异 → 价值因果 → 可观察效果”链路。只写“采用某机制”或只写“提升效率、增强安全”等泛化价值时阻塞。
- `INV-007`：每项必须提供来源事实支持的“已实现基础”，写清技术对象、触发或输入、实际处理、必要约束以及输出或状态。每项拟扩展保护必须在 manifest 中引用唯一 `IE` 台账项；对外正文使用不带编号的独立 `> **拟扩展保护**` 引用块，无扩展时不显示空占位块；`IE` 映射集中写入内部追溯附录。缺少实现依据、扩展与 `IE` 台账不一致、存在孤立 `IE`、把扩展写成已实现、扩展正文未高亮、显示空扩展块或对外泄露 `IE` 时阻塞。
- `INV-008`：“是否还有其他解决方案”不得再次以普通段落或列表呈现拟扩展内容；存在扩展时只引用对应创新点下的高亮块，不存在扩展时写“无”。

对比基线优先引用来源事实中的现有做法。没有可靠外部证据时可写通用技术基线，但不得把它包装成某个具名竞品的事实。

“已实现基础”应比抽象主张更具体，但必须先泛化内部实现：保留技术对象、输入输出、关键步骤、状态变化、接口边界和必要约束；删除类名、函数名、字段名、表结构和未经授权的内部产品名。每个创新点都必须以已实现基础为主，扩展保护只能覆盖等价机制、参数范围或部署变体；扩展内容同样不得泄露内部标识。

正例：现有做法按单条越界记录派单；本方案在不改变采集频率的约束下按阶段窗口聚合并只保留一张活动处置单；差异是处置对象由单条记录变为阶段事件集合；因此同一窗口的活动处置单数量可观察为不超过一，对应 T1。

反例：“采用阶段化窗口处理异常，提高效率。”这句话只有处理方式和泛化好处，没有对比基线、实质差异及可观察价值。

字段、数量、编号、实现来源引用、`IE` 双向绑定、扩展块高亮、内外版本隔离、双向 `I/T` 引用、悬空落点和孤立泛化价值可自动检查；“是否确实已经实现”、真正的新颖性、实质差异和价值因果仍需用户确认、检索与专业评审判断。

## 7. 技术效果与因果映射

### EFF：I/T 双射

- `EFF-001`：保留 2–4 个 `T1...Tn`，编号连续。
- `EFF-002`：每项效果必须写全原问题、采用机制、可观察结果和验证状态。
- `EFF-003`：每个 `I` 通过 `effect_id` 绑定唯一 `T`，每个 `T` 通过 `innovation_id` 反向绑定唯一 `I`，两个方向必须一致；没有实测材料时只能标记 `expected_observable`。
- `EFF-004`：禁止只写“提升效率、增强安全、优化体验”等不可观察结论。
- `EFF-005`：`verified` 必须通过 `evidence_source_ids` 绑定已有 `SF/EM`；没有可核验材料时只能标记 `expected_observable`。

正例：原问题为重复派单；采用窗口聚合机制；可观察结果为同一窗口只形成一张处置单；状态为预期可观察。

反例：I1 对应“提高系统安全性”，没有机制、观察方式和验证状态。

双射、字段和状态可自动检查；机制是否足以产生结果由因果删除测试复核。

## 8. 语义复核

### REV：两类必做测试

- `REV-001`：泛化替换测试。把领域名词换成任意行业名词后内容仍成立，判为 `fail`。
- `REV-002`：因果删除测试必须逐项覆盖全部创新点。
- `REV-003`：删除核心机制后对应效果仍成立，判为 `fail`；`fail` 导致 `blocked`，`pending` 导致 `review_required`。
- `REV-004`：SVG 视觉复核必须逐图覆盖，并记录 `pass/fail/pending`。
- `REV-005`：每项视觉复核必须绑定当前 `svg_sha256`，图变化后旧复核失效。

复核记录必须包含复核人、状态和理由。因果删除测试必须覆盖每个创新点；不能用一条总评代替。

正例：删除阶段化窗口后，无法形成“同一阶段窗口内只生成一张处置单”的结果，因此 I1/T1 因果成立。

反例：删除所有核心机制后，“提升管理水平”仍成立，却记录为通过。

## 9. 来源、术语与竞品证据

### EVD：三类来源

- `EVD-001`：来源台账必须包含来源事实、发明扩展、外部资料、术语泛化和缩写白名单。
- `EVD-002`：每项来源事实必须有编号、陈述和输入定位。
- `EVD-003`：每项发明扩展至少引用一个已存在的来源事实编号。
- `EVD-004`：外部资料必须有标题、定位地址、检索日期和 `public_fact` 或 `reasonable_inference` 属性。
- `EVD-005`：类名、函数、字段、表名默认转为通用技术表达；必要缩写进入白名单。

正例：`SF1` 记录用户提供的重复派单现象；`IE1` 基于 SF1 提出窗口聚合处置对象。

反例：把数据库字段值、内部类名和未提供的上线日期直接写成来源事实。

### CMP：竞品与相似方案

- `CMP-001`：竞品研究状态只允许 `evidence_found` 或 `searched_no_usable_evidence`；前者必须有 1–3 项完整证据，后者必须没有具名竞品证据。
- `CMP-002`：每项证据必须包含名称、相关业务/产品、公开 HTTP(S) 定位地址、检索日期和证据属性；证据定位与日期必须回溯到实际检索记录，确定无效的本地域名和保留测试域名直接阻塞。
- `CMP-003`：无论用户是否提供竞品输入，都必须至少记录两组不同检索式，且同时覆盖“技术对象”和“核心机制”焦点，并包含检索日期、实际查阅页面和结果摘要。无可用证据状态只能使用固定无具名断言结论；缺少检索工具或检索记录时阻塞最终成稿。
- `CMP-004`：对外竞品章节必须从 manifest 原样呈现检索范围、日期、结论及可用证据；禁止留空、输出“待检索”或在无证据状态下裸写具名竞品能力。
- `CMP-005`：每组检索通过 `basis_terms` 绑定同时存在于输入完整性和关键词中的焦点术语，并通过 `context_terms` 绑定另一技术分类或已确认使用场景；两类词必须以纯文本原样出现在检索式中，检索式还必须带有产品、官方、专利、论文、标准或相似方案等研究限定词。HTML entity、零宽/控制字符，以及只塞入依据词但缺少上下文或研究意图的查询均阻塞。

正例：用户未提供竞品时，使用泛化后的技术对象和核心机制分别检索官方产品页，记录两组检索过程；找到可靠资料则列出相应产品，没有可用资料则说明查阅范围及无法形成具名对比的原因。

反例：因为用户没有提供竞品名称，直接输出“待检索”；只执行一条宽泛查询便声称已完成行业分析；或把“策略请求”放在咖啡机价格查询前面伪装成相关检索。

外部事实真实性和页面实时可访问性不由离线脚本证明；脚本验证证据记录是否完整、自洽并排除确定无效地址，实际检索与页面核验仍由执行阶段完成。脚本只确认检索式含有已绑定的技术依据、上下文和研究意图词，不判断其余自由文本是否与主题语义相关；执行阶段必须复核整条检索式和结果页面，不能把本地通过当成检索真实性证明。

## 10. 交付包同源校验

### SCH / DOC：Schema 与正文内容同源

- `SCH-001`：主入口直接执行随 skill 分发的 JSON Schema 合同；缺字段、额外字段、类型、枚举、数量、格式或条件约束不匹配均阻塞。
- `DOC-001`：Markdown 标题必须与 `manifest.patent.title` 完全一致。
- `DOC-002`：完整包必须保留固定模板的全部三级章节；只有两个二级标题不构成交底书。
- `DOC-003`：使用场景、核心发明主张、关键词以及每个 `I/T` 的公开语义字段必须从 manifest 原样渲染；创新点中的已实现基础、拟扩展保护、对比基线、实质差异、价值关联和 `T` 编号必须连续呈现，允许在其后补充解释，但不得另写一套内容。来源编号、证据编号和机器枚举不属于公开语义字段。
- `DOC-004`：交底书目录根部的 `disclosure.md` 是唯一对外版本，禁止出现内部台账编号、内部事实定位、`来源依据` 标签、内部追溯附录、除规范 `diagram-id` 外的 HTML 注释，以及 `expected_observable/verified/public_fact/reasonable_inference/evidence_found/searched_no_usable_evidence` 等机器枚举；公开竞品资料的来源链接不属于内部事实定位，状态必须转写为自然中文。
- `DOC-005`：`disclosure-workspace/disclosure-internal.md` 的公开正文必须与根部 `disclosure.md` 完全一致，只能在文末追加唯一的“内部追溯附录（禁止对外）”；附录必须覆盖 manifest 中的全部来源事实、发明扩展、外部资料及创新/效果证据映射。

### PKG：文件与 hash

- `PKG-001`：交底书目录必须存在。
- `PKG-002`：根部 `disclosure.md` 与工作区中的 `disclosure-manifest.json` 必须存在且可读取。
- `PKG-011`：工作区必须额外包含可读取的 `disclosure-internal.md`，不得用单一文档同时充当对外版和内部版。
- `PKG-012`：新产出固定采用“根部唯一外发稿 + `disclosure-workspace/` 内部工作区”布局；内部稿、manifest、验证报告、图包和落盘的检索/思路/草稿不得与外发稿并列，工作区内也不得复制 `disclosure.md`。新旧 manifest 同时存在或工作区越出交底书目录时阻塞。
- `PKG-013`：校验器仅为历史交付物兼容旧平铺布局并给出警告；生成流程不得继续创建旧布局。
- `PKG-003`：文档标题和 manifest `schema_version` 必须符合合同。
- `PKG-004`：文档和 manifest 不得残留模板占位符。
- `PKG-005`：所有 manifest 路径必须是相对 `disclosure-workspace/` 的内部路径，禁止绝对路径和 `..`。
- `PKG-006`：manifest 声明的图包目录及四类文件必须存在、解析后仍位于图包内，文本工件必须为可读 UTF-8。
- `PKG-007`：图包 `validation.json` 必须使用 v1.1，并与图示编号和 profile 版本一致。
- `PKG-008`：brief、PlantUML、规范化 PlantUML、SVG 的实际 hash 与 artifact 路径必须和图包记录一致。
- `PKG-009`：Markdown 内嵌 PlantUML 的规范化 hash 必须与图包同源。
- `PKG-010`：每个图包必须再次通过直接依赖的 v1.1 verifier；路径、状态不变量、实际指标或双向 artifact 合同不一致时阻塞。

草稿兼容入口使用 `PKG-900...PKG-904`：它只验证文件、标题、占位符、固定章节和基本编号，并始终提示缺少完整包、hash 与语义/视觉复核。

正例：D1 的四份图包文件、manifest 路径、Markdown 标识和视觉复核 hash 完全一致。

反例：只替换 Markdown 中的 PlantUML，仍沿用旧图包和旧视觉复核结论。

## 11. 验证能力边界

本地门禁可以确定：结构、数量、编号、字段、引用、路径、hash、图包状态和复核记录状态。

本地门禁不能单独确定：

- 外部材料是否真实、完整或最新。
- 发明是否具备专利新颖性、创造性或可专利性。
- 业务域和系统边界是否符合真实组织责任。
- 机制与效果在真实环境中是否成立。
- SVG 是否绝对不存在交叉或遮挡。

因此最终验证报告必须保留这些边界；未获得脱敏真实 Session 前，只能声明合成回归通过，不能声明真实 Session 已覆盖。
