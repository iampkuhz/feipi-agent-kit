# 审查标准

以本轮用户任务和实际交付为依据，检查以下五个问题。标准用于判断问题，不是要求每条消息固定包含五个部分。

| 问题 | 检查与修正 |
| --- | --- |
| 用户知道发生了什么吗？ | 先呈现与任务有关的结果或变化；将部分完成、失败和验证限制放在对应事项旁。过程、内部角色和工具输出只保留理解结果所需的部分。 |
| 用户有足够依据判断吗？ | 决策说明保留必要理由、主要取舍和影响；材料缺事实则核实或明确缺口，不编造数字、收益、保证与用户立场。语义解释和文字精炼按实际需要处理。 |
| 当前界面里能读吗？ | 宽表格、长日志、深层列表或长代码妨碍手机阅读时，提炼摘要，按事项分段；完整证据放可用的详情入口。保留重要差异，不把必要复杂内容一概压成短句。 |
| 必要产物能查看吗？ | 区分文件存在、可上传、已上传和用户能访问；本机路径或 localhost 不是已验证的手机入口。使用已核实的原生入口、附件或链接，能力不足时将必要内容放正文并说明限制。 |
| 用户知道下一步吗？ | 明确是否需要用户行动；需要时说明做什么、影响哪里及可用回复方式。已授权或可自行完成的工作继续执行；无需决策的结果不增加“请确认”。 |

## 问题反馈

给原 Agent 的意见应能直接用于修订，例如：

> 定位：结尾“详情在本机 report.html，请确认”。影响：正文没有结论，只有未经验证的电脑入口，“确认”也没有对应动作。修正：补充已有结论和待决定事项，通过现有可用渠道交付详情。通过条件：正文足以理解决定，详情入口的交付状态明确，回复与后续动作一一对应。

一项问题可以涉及内容、产物与渠道，但应说明首先缺失在哪里。不要把所有问题归为“文风不好”或只要求“再精简”。

## 复审与不足

- 将最终稿与原始事实对照：数值、范围、条件、状态、否定和剩余工作不能在摘要或拆分时改变。没有完成的检查不能计为通过。
- 文案通过、产物访问已核实、实际接收或手机实显分别陈述；没有客户端证据时保留未验证范围。
- 确认必须绑定当前方案和动作；方案或影响发生实质变化后，不沿用旧确认。查看报告和询问原因不构成执行批准。
- 确有缺口时交付可确定部分及缺口影响；能够在已有授权内补齐的事实或入口由 Agent 处理，不默认转交用户。
