# 常见反模式

## 先画图，后补需求

- 表现：用户只有一句抽象目标，就直接开始写 PlantUML。
- 问题：组件、边界和流程会被模型脑补，后续很难核对责任边界。
- 修复：先补 brief，至少写清核心元素、关系两件事。Fallback 模式下可先生成草图，但需标注"未结构化"。

## 把模板、样例、规则各写一份

- 表现：模板注释写一套规则，说明文档再写一套，脚本里还有第三套。
- 问题：规则一改就漂，维护成本迅速失控。
- 修复：schema 作为唯一真相，模板只示例，文档只解释。

## 组件名和 alias 不一致

- 表现：brief 写 `order_service`，图里却用了 `orderService` 或 `orders`。
- 问题：覆盖校验无法自动化，图和需求无法机械比对。
- 修复：alias 只来自 brief 中的 `id` 字段，不要重新命名。

## 只看源码不看渲染

- 表现：`.puml` 看起来没问题，就直接交付。
- 问题：真实渲染时常见重叠、过宽、标签遮挡。
- 修复：至少执行渲染脚本；若环境不可用，明确标注为未完成真实渲染校验。

## 扩大 renderer 进程管理

- 表现：超出 preflight 的固定一次 Podman 启动，继续杀死、重启、轮询或排查 PlantUML proxy。
- 问题：作图 skill 越权承担运行时运维，单次 session 无法及时停止。
- 修复：首次探测失败只执行一次固定启动命令并复检一次；仍不可用立即 `blocked`。

## 把审美问题放进自动修复循环

- 表现：SVG 已通过确定性校验，仍因主观排版偏好反复修改和渲染。
- 问题：视觉目标没有机械收敛条件，会放大上下文和 renderer 耗时。
- 修复：自动循环只处理 syntax、coverage、layout；审美意见交给 reviewer。

## 静态规则与 renderer 冲突时仍只改图

- 表现：静态接受的活动声明被 renderer 拒绝，改为条件分支后校验器又报告跨分支连线。
- 问题：校验器和样例语法失配，继续压缩图或增加权限不能修复控制流解析。
- 修复：退出图面重试，明确报告工具缺陷；在目标 skill 维护授权内修规约、解析器与正反例，再运行真实渲染验证。

## 正向样例允许 blocked 也算通过

- 表现：测试仅确认静态字段，接受 `final_status=success` 或 `blocked`。
- 问题：样例永远无法渲染也能让测试全绿，规约缺陷会被复制到后续任务。
- 修复：正向样例必须 `render_result=ok` 且 `final_status=success`；错误样例和 renderer 不可用测试独立维护，不能冒充成功链路。
